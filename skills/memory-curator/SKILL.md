# Memory Curator (`/memory-curator`, `/mcur`)

메모리와 하네스는 추가는 자동으로 되지만 정리는 저절로 되지 않음. 그대로 두면 사용자도 모르는 규칙이 쌓이고, 모델이 바뀐 뒤에는 예전 약점을 막던 규칙이 오히려 이상한 동작을 만듦. 이 스킬은 추가는 자동에 맡기고, 분류·정제·검증만 주기적으로 사람의 확인을 거쳐 처리함.

## 핵심 원칙

- 남길 기준은 하나: "Claude가 대화나 프로젝트 자료만 보고는 알 수 없고, 있으면 답변이 실제로 달라지는가"
- 반영은 항상 사용자 확인 후. 변경안을 먼저 보여주고, 승인된 항목만 적용함
  - Claude.ai: 승인 전에는 memory_write·memory_str_replace·memory_delete를 호출하지 않음
  - Claude Code: 파일을 직접 고치지 않고 별도 브랜치나 패치로만 제안함. 커밋은 사람이 함
- 변경이 없는 것도 정상 결과임. 정리할 거리를 억지로 만들지 않음
- 각 규칙이 막으려는 실패가 무엇인지 모르면 지우지 말고 "출처 불명"으로 따로 표시해 사용자에게 물음

## 0. 실행 환경과 단계 선택

먼저 대상과 환경을 한 줄로 확인함.

- 대상: Claude.ai 메모리 / Claude Code 프롬프트 파일(CLAUDE.md, AGENTS.md, 스킬, 훅) / 둘 다
- 환경: 격리 서브에이전트 가능(Claude Code, Cowork) / 불가(Claude.ai 채팅 → Lite). 이 판정은 이 스킬이 내리고, 이후 단계에서 다른 스킬의 표시에 기대지 않음
- sfumato 설치 여부: 없으면 2단계는 건너뛰고 그 사실을 한 줄로 알림
- 단계: 사용자가 정하지 않으면 1→3을 기본으로 돌림. 2는 분류 체계를 처음 잡을 때, 사용자가 요청할 때, 또는 1에서 "어느 파일에도 맞지 않는 항목"이 3개 이상 나올 때만 제안함
  - 2는 비용이 크므로 제안만 하고, 사용자가 동의해야 실행함

## 1. 정기 정제 (수렴)

1. 전체 목록을 확보함
   - Claude.ai: memory_list 후 관련 파일을 한 번의 memory_read로 묶어 읽음
   - Claude Code: 프롬프트 파일과 스킬·훅 디렉터리, 최근 git log를 읽음. 사람이 쓴 줄과 Claude가 덧붙인 줄을 git blame으로 구분할 수 있으면 구분함
2. 항목마다 아래 중 하나로 판정함
   - 유지
   - 병합: 같은 내용이 다른 파일·다른 표현으로 반복됨
   - 이동: 내용과 파일 주제가 맞지 않음 (한 주제 한 파일)
   - 갱신: 진행 상황이 바뀌었거나 끝남. 사용자가 이번 대화에서 말한 사실이 있을 때만
   - 삭제: 끝난 일의 일시적 상태, 대화·자료에서 다시 알 수 있는 내용, 답변을 바꾸지 않는 장식성 정보
   - 출처 불명: 왜 들어갔는지 알 수 없는 규칙
3. 분류 상태를 함께 점검함
   - 파일 설명(description)이 내용과 맞는지
   - 너무 커진 파일은 쪼갤지, 너무 작은 파일 여럿은 합칠지

판정할 때 지켜야 할 것

- 다른 표면이 쓴 줄([observed], [inferred], (for=code) 표시, 날짜만 있는 Claude Code 기록)은 판정만 하고, 사용자가 명시하지 않으면 원문 그대로 둠
- 민감 정보 규칙(건강·재정·신원 등)에 걸리는 항목을 새로 만들거나 바꿔 쓰지 않음. 이미 들어 있으면 삭제 후보로만 표시함
- 프로젝트 세션에서는 해당 프로젝트 하위 경로에만 쓸 수 있음. 계정 단위 파일의 변경이 필요하면 일반 채팅에서 하라고 안내함

## 2. 체계 재편 (발산, 선택)

주제별 분류는 같은 구조를 공유하는 주제들의 연결을 놓침. 예를 들어 서로 다른 프로젝트가 같은 물리적·조직적 구조를 공유할 수 있음.

1. 현재 파일 목록과 각 설명만 뽑아 "더 나은 분류 축을 찾는 문제"로 3~5줄 문제 정의를 만듦
   - 금지할 뻔한 답: 단순 알파벳·날짜 정렬, 업무/개인 이분법, 태그 남발
2. sfumato에 그 문제 정의를 넘겨 실행함. sfumato의 절차·비용 규칙을 그대로 따르되 아래는 이 스킬이 보장함
   - 모드는 기본 dual-track. `/sfm-max`와 `deep`은 사용자가 따로 요청할 때만
   - 샘플러에는 `--safe-profile claude`를 붙이고, `python`이 없어 실패하면 `python3`로 다시 실행함
   - 0단계에서 Lite로 판정했으면 sfumato 출력에 표시가 있든 없든 결과 제목에 "Lite — 단일 맥락 근사"를 붙임. sfumato 원본에는 Claude.ai 채팅용 처리가 없어서 격리 없이 돈 사실을 스스로 밝히지 않을 수 있음
3. sfumato 결과에서 채택할 분류 축을 고르고, 기존 파일을 새 축으로 옮기는 매핑안을 만듦
   - 축 이름과 근거 한 줄, 옮겨질 파일 목록, 별칭(aliases)으로 남길 옛 이름
4. 매핑안은 1단계 변경안과 합쳐 3단계 검증으로 넘김

## 3. 블라인드 검증 (반박)

변경안을 만든 맥락은 그 변경을 정당화하는 쪽으로 기움. 그래서 판정 근거를 보지 않은 검증자가 변경 하나하나를 반박하도록 함.

- 서브에이전트 가능: 변경안마다 새 서브에이전트를 띄워 [references/verifier_prompt.md](./references/verifier_prompt.md)의 템플릿을 그대로 씀. 검증자에게는 항목 원문, 제안된 변경, 남길 기준만 주고 판정 근거와 대화 맥락은 주지 않음
- Lite(Claude.ai): 같은 템플릿을 쓰되, 판정 근거를 다시 읽지 않고 항목 원문과 변경만 보고 판단함. 결과에 "Lite — 단일 맥락 근사"라고 표시함

검증 결과는 셋 중 하나

- 통과: 변경해도 답변 품질이 떨어지지 않음
- 보류: 판단할 정보가 부족함 → 사용자에게 질문으로 넘김
- 기각: 이 정보가 없으면 특정 상황에서 답변이 틀려지거나 위험해짐 → 변경안에서 뺌

## 4. 보고와 반영

보고는 사용자의 문서 규칙을 따름. 표 대신 목록, 핵심만, 항목 끝은 명사형 종결.

1. 첫 줄에 한 문장 요약: 검토 항목 수, 변경안 수, 기각 수, Lite 여부
2. 통과한 변경을 종류별로 묶어 제시함
   - 삭제·병합·이동·갱신 각각 "무엇을 → 어떻게, 이유 한 줄"
3. 보류와 출처 불명 항목은 질문으로 따로 제시함
4. 기각된 변경은 한 줄씩만 남겨, 무엇을 지키려고 남겼는지 보이게 함
5. 사용자가 승인한 항목만 반영함
   - Claude.ai: 일반 항목을 먼저, 민감 경계에 가까운 항목은 나중에 별도 호출로 반영함. 실패하면 그대로 알림
   - Claude Code: `memory-curation/YYYY-MM-DD` 브랜치에 커밋 없이 변경을 올리거나 패치 파일로 남기고, 사용자가 diff를 확인해 커밋하게 함
6. 다음 정제 권장 시점을 한 줄로 제안함 (기본 한 달, 모델 세대가 바뀐 직후면 즉시 전수 리셋 검토)

## 하네스 리셋 모드

사용자가 "싹 밀고 테스트"를 원하면 1~3 대신 이 순서로 진행함.

1. 백업: Claude Code는 현재 상태를 태그나 브랜치로 남기고, Claude.ai는 전체 내용을 내보내 사용자에게 파일로 줌
2. 최소 하네스로 대체: "프로젝트 안에서 알 수 없는 정보"만 남긴 몇 줄짜리 버전을 제안함
3. 문제가 다시 보일 때만 백업에서 해당 규칙을 하나씩 되돌리고, 되돌린 이유(막으려는 실패)를 규칙 옆에 한 줄로 적음
